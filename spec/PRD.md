# מסמך דרישות מוצר (PRD) — Ordan Cargo Future Clients

## 1. רקע ומטרות

### א. מטרת המוצר
**Ordan Cargo Future Clients** היא מערכת Web לשימוש פנימי בחברה בלבד. המערכת מחלצת אוטומטית לקוחות פוטנציאליים (לידים) מקובצי PDF מסוג House Bill of Lading (HBL), שומרת את פרטי ה-Consignee ופרטי המשלוח במאגר, ושולחת מייל שיווקי אוטומטי כשקיימים כל הנתונים הדרושים.

### ב. תיאור הבעיה
קובצי HBL שמגיעים לחברה מכילים פרטי Consignee שעשויים להפוך ללקוחות של Ordan Cargo. כיום עובדים מחלצים את הפרטים מהמסמכים, בודקים כפילויות ופונים ללקוחות באופן ידני, וזה דורש זמן ועבודה.

בנוסף, לעיתים חסרים במסמך פרטים הנדרשים לתהליך, או שהחילוץ או שליחת המייל נכשלים. במקרים אלה נדרש מנגנון ברור שמעביר את המקרה לטיפול ידני.

### ג. תיאור הפתרון
המשתמש מעלה ידנית PDF דיגיטלי של HBL, והמערכת מבצעת את שאר התהליך אוטומטית:

1. חילוץ פרטי ה-Consignee: Company Name, Address, Phone ו-Email.
2. חילוץ פרטי המשלוח: נמל מוצא, מדינת מוצא, נמל יעד, תנאי מכר (Incoterms) וסוג משלוח (FCL/LCL).
3. בדיקת כפילות מול מאגר הלקוחות.
4. שמירת לקוח חדש במאגר, כולל פרטי המשלוח.
5. שליחת מייל שיווקי אוטומטי, כשקיימים כל הנתונים הדרושים.
6. כשחסר מידע או מתרחשת שגיאה: שמירת המידע שניתן לחלץ ושליחת התראה למשתמש לטיפול ידני, לפי הכללים במסמך זה.

### ד. חזון ה-MVP ומדדי הצלחה
מטרת ה-MVP היא תהליך אוטומטי מקצה לקצה עבור PDF בודד: העלאה, חילוץ, בדיקת כפילות, שמירה ושליחת מייל שיווקי. כשכל הנתונים קיימים, אין צורך בהתערבות ידנית. התערבות ידנית נדרשת רק כשחסר מידע, כשהחילוץ נכשל או כששליחת המייל נכשלת.

**קריטריוני הצלחה.** במקרים תקינים, המערכת מבצעת ללא התערבות ידנית את כל השלבים הבאים:
1. קבלת ה-PDF ועיבודו.
2. חילוץ נכון של פרטי ה-Consignee ופרטי המשלוח.
3. זיהוי כפילויות לפי הכללים.
4. שמירת לקוח חדש.
5. שליחת המייל השיווקי.
6. העברת מקרים חריגים לטיפול ידני.

**KPI:** עיבוד מוצלח של לפחות 90% מהמסמכים.

## 2. קהלי יעד וצרכי משתמשים

### א. User Personas — פרסונות משתמשים

#### מנהל המערכת (משתמש יחיד)
ב-MVP יש משתמש יחיד במערכת. זהו עובד החברה שמקבל קובצי HBL ומעלה אותם למערכת.

המשתמש צריך:
- להעלות קובצי HBL במהירות.
- לסמוך על המערכת שתבצע את עיקר התהליך באופן אוטומטי.
- לצפות ברשימת הלקוחות שנאספו, ולחפש, לסנן ולמיין אותה.
- לזהות במהירות מקרים שדורשים טיפול ידני.
- לצפות בפרטי לקוח, בפרטי המשלוח ובשגיאות.
- לערוך או למחוק לקוחות לפי הצורך.

### ב. User Stories — סיפורי משתמש

- כמשתמש, אני רוצה להעלות קובץ PDF של HBL, כדי שהמערכת תחלץ ממנו את פרטי הלקוח ופרטי המשלוח באופן אוטומטי.
- כמשתמש, אני רוצה שהמערכת תבדוק אם הלקוח כבר קיים, כדי שלא ייווצרו כפילויות ולא יישלחו פניות חוזרות לאותו איש קשר.
- כמשתמש, אני רוצה שלקוח חדש יישמר אוטומטית יחד עם פרטי המשלוח, כדי שאוכל לנהל מאגר מסודר של לקוחות פוטנציאליים.
- כמשתמש, אני רוצה שהמערכת תשלח מייל שיווקי אוטומטי כשכל המידע הדרוש קיים, כדי לצמצם עבודה ידנית.
- כמשתמש, אני רוצה לקבל מייל באנגלית עם ה-PDF והסבר כשנדרש טיפול ידני, כדי שאוכל להשלים את התהליך בעצמי.
- כמשתמש, אני רוצה לראות את סטטוס העיבוד ואת סטטוס המייל של כל לקוח, כדי להבין במהירות מה קרה בתהליך.
- כמשתמש, אני רוצה לחפש ולסנן לקוחות, כדי לאתר לקוחות או תקלות במהירות.
- כמשתמש, אני רוצה לפתוח מסך פרטים של לקוח, כדי לראות את כל המידע, כולל פרטי המשלוח והשגיאות.
- כמשתמש, אני רוצה לערוך את פרטי הלקוח ולשמור את השינויים, כדי לתקן או להשלים מידע באופן ידני.
- כמשתמש, אני רוצה למחוק לקוח לאחר אישור, כדי להסיר רשומות שאינני רוצה לשמור.

## 3. זרימות וחוויית משתמש

### א. User Journey — מסע המשתמש

#### תרחיש מרכזי: עיבוד מוצלח
1. המשתמש מקבל קובץ HBL, נכנס למערכת ומגיע למסך **Clients**.
2. המשתמש עובר דרך ה-Top Navigation למסך **Upload PDF**.
3. המשתמש גורר את ה-PDF לאזור ה-Drag & Drop, או בוחר אותו מהמחשב.
4. העיבוד מתחיל אוטומטית, ומוצג חיווי **Processing** ברור.
5. המערכת מחלצת את פרטי ה-Consignee ואת פרטי המשלוח.
6. המערכת בודקת אם הלקוח כבר קיים.
7. אם הלקוח חדש, המערכת שומרת אותו יחד עם פרטי המשלוח.
8. אם קיימים כל הנתונים הדרושים, המערכת שולחת מיד מייל שיווקי.
9. המשתמש נשאר במסך ההעלאה, ובחלק העליון מוצגת הודעה שהקובץ עובד בהצלחה.
10. אזור ההעלאה נשאר זמין להעלאת קובץ נוסף.

#### תרחיש כפילות
1. המערכת מחלצת את פרטי הלקוח.
2. המערכת מזהה, לפי כללי הכפילות, שהלקוח כבר קיים.
3. המערכת מדלגת על הרשומה בשקט, בלי להציג הודעה מיוחדת.
4. לא נוצרת רשומה חדשה, והרשומה הקיימת לא משתנה. Date Added ופרטי המשלוח של ה-HBL הראשון נשמרים כמו שהם.
5. לא נשלח מייל נוסף.

#### תרחיש טיפול ידני
1. המערכת מעבדת את ה-PDF.
2. מתגלה מידע חסר או שגיאה שמחייבים טיפול ידני.
3. המערכת שומרת את המידע שאפשר לשמור, לפי הכללים.
4. הסטטוסים מתעדכנים לפי סוג הבעיה.
5. המערכת שולחת למשתמש מייל באנגלית עם ה-PDF המקורי, הסבר על הבעיה וכל המידע הרלוונטי שחולץ.
6. המשתמש פותח את הלקוח במסך Client Details, רואה את פרטי השגיאה ומשלים או מתקן ידנית.

### ב. User Flows — זרימות משתמש

#### Flow 1: העלאת PDF
`Clients → Upload PDF → Drag & Drop / Select PDF → Processing → עיבוד אוטומטי → הודעת הצלחה → Upload PDF נשאר פתוח`

#### Flow 2: צפייה בלקוחות
`Clients → Search / Filters / Sort / Pagination → בחירת לקוח → Client Details`

#### Flow 3: עריכת לקוח
`Client Details → Edit → שינוי פרטים → Save / Cancel`

בלחיצה על **Save** הנתונים נשמרים כפי שהוזנו, ללא ולידציה. עריכה ידנית לא מפעילה שליחה של מייל שיווקי.

#### Flow 4: מחיקת לקוח
`Client Details → Delete → הודעת אישור → Confirm → מחיקה סופית`

אין אפשרות Undo או שחזור.

### ג. UX Requirements — דרישות חוויית משתמש

- ממשק פשוט, נקי ומקצועי.
- כל טקסטי הממשק באנגלית.
- המערכת מיועדת ל-Desktop Web בלבד.
- שם המערכת מוצג בחלק העליון: **Ordan Cargo Future Clients**.
- הניווט הוא Top Navigation, עם שני פריטים: **Clients** ו-**Upload PDF**.
- **Clients** הוא מסך הבית וברירת המחדל.
- בזמן עיבוד PDF מוצג חיווי Processing ברור.
- בסיום העיבוד מוצג במסך Upload PDF אישור הצלחה בלבד, ללא שם הקובץ.
- במסך Clients אין הודעת הצלחה נפרדת. הרשומה החדשה פשוט מופיעה בטבלה.
- ערכים חסרים מוצגים כ-`NOT Available`.

## 4. דרישות פונקציונליות

### א. Features & Functional Requirements — פיצ'רים ודרישות פונקציונליות

### 4.1 מסך Clients
מסך הבית של המערכת.

#### טבלת לקוחות
עמודות הטבלה:
- **Company Name**
- **Email**
- **Phone**
- **Date Added**
- **Processing Status**
- **Email Status**

פרטי המשלוח לא מוצגים בטבלה.

#### יכולות הטבלה
- חיפוש לפי Company Name, Email ו-Phone.
- סינון לפי Processing Status ולפי Email Status. המטרה היא להגיע במהירות למקרים שדורשים טיפול ידני, כמו `Failed` או `Requires Manual Review`.
- מיון, כולל לפי Date Added. אפשר להציג את הלקוחות החדשים ביותר ראשונים.
- Pagination, עם 25 לקוחות בעמוד כברירת מחדל.
- כפתור **Refresh** לרענון ידני של הנתונים.
- לחיצה על לקוח פותחת את מסך **Client Details**.

### 4.2 מסך Client Details
מסך נפרד שמציג את פרטי הלקוח בצורה גדולה וברורה.

סדר השדות:
1. **Company Name**
2. **Address**
3. **Phone**
4. **Email**
5. **Origin Port**: נמל מוצא.
6. **Origin Country**: מדינת מוצא.
7. **Destination Port**: נמל יעד.
8. **Incoterms**: תנאי מכר.
9. **Shipment Type**: FCL/LCL.
10. **Date Added**
11. **Processing Status**
12. **Email Status**
13. **Error Details**: מוצג רק כשקיימת שגיאה או סיבה לטיפול ידני.

#### עריכה
- כפתור **Edit**. במצב עריכה מוצגים הכפתורים **Save** ו-**Cancel**.
- השדות הניתנים לעריכה: Company Name, Address, Phone, Email.
- *הנחה:* פרטי המשלוח מוצגים לקריאה בלבד ואינם ניתנים לעריכה.
- הנתונים נשמרים בדיוק כפי שהוזנו, ללא ולידציה.
- עריכה ידנית לא שולחת מייל שיווקי.
- לא נשמר Last Updated.

#### מחיקה
- לפני המחיקה מוצגת הודעת אישור: `Are you sure you want to delete this client?`
- אחרי האישור, המחיקה סופית ומיידית, ללא Undo או שחזור.

### 4.3 מסך Upload PDF
- מסך ייעודי להעלאת PDF, עם תמיכה ב-Drag & Drop ובבחירת קובץ מהמחשב.
- קובץ PDF אחד בכל עיבוד.
- העיבוד מתחיל אוטומטית מיד אחרי בחירת הקובץ, בלי שלב אישור.
- במהלך העיבוד מוצג חיווי Processing.
- בסיום העיבוד המשתמש נשאר במסך, ובחלק העליון מוצגת הודעת הצלחה. אזור ההעלאה נשאר זמין.
- המערכת מקבלת קובצי PDF בלבד. ניסיון להעלות פורמט אחר נחסם, ומוצגת ההודעה: `Only PDF files are supported.`
- אם ההעלאה נכשלת מסיבה טכנית, מוצגת הודעת שגיאה באנגלית וכפתור **Try Again**.

### 4.4 חילוץ מידע מה-PDF
- ה-MVP מיועד לקובצי PDF דיגיטליים של HBL עם טקסט שאפשר לחלץ. אין צורך ב-OCR.
- בכל מסמך יש Consignee אחד בלבד.
- המערכת לא מנחשת ולא משלימה מידע. כל שדה נלקח רק אם הוא מופיע בפועל במסמך.

#### שדות לחילוץ ולשמירה ברשומת הלקוח
| קבוצה | שדה |
|---|---|
| Consignee | Company Name, Address, Phone, Email |
| פרטי משלוח | Origin Port (נמל מוצא), Origin Country (מדינת המוצא שממנה המשלוח יצא בפועל), Destination Port (נמל יעד), Incoterms (תנאי מכר), Shipment Type (FCL או LCL) |

בנוסף נשמרים:
- **Date Added**: התאריך שבו הלקוח נוסף לראשונה.
- Processing Status ו-Email Status.
- Error Details, כשרלוונטי.

### 4.5 כללים למידע חובה ולמידע חסר

#### Company Name
Company Name הוא שדה חובה לעיבוד אוטומטי מלא. אם הוא חסר:
- שאר המידע שחולץ נשמר.
- Processing Status = `Failed`.
- התהליך האוטומטי לא מושלם, ולא נשלח מייל שיווקי.
- נשלח למשתמש מייל באנגלית עם ה-PDF והסבר שנדרש טיפול ידני.

אם המשתמש משלים Company Name ידנית ושומר, Processing Status משתנה ל-`Success`. לא נשלח מייל שיווקי.

#### Address / Phone
- שדות אלה אינם חובה. רשומה בלעדיהם יכולה להיות `Success`.
- הם אינם תנאי לשליחת המייל השיווקי.
- כשהם חסרים, הם מוצגים כ-`NOT Available`.

#### Email
אם Email חסר:
- הלקוח נשמר עם המידע שנמצא.
- Email Status = `Missing Email`.
- לא נשלח מייל שיווקי.
- נשלח למשתמש מייל באנגלית עם ה-PDF לבדיקה ידנית.

אם המשתמש מוסיף Email ידנית, Email Status משתנה ל-`Email Added Manually`. לא נשלח מייל שיווקי.

#### פרטי משלוח
- פרט משלוח חסר מוצג כ-`NOT Available`.
- ההשפעה של פרט משלוח חסר על המייל השיווקי מפורטת בסעיף 4.8.

### 4.6 מניעת כפילויות
המערכת בודקת כפילויות לפני שהיא יוצרת לקוח חדש.

| מצב | כלל |
|---|---|
| קיים Email | **Company Name זהה + Email זהה** = לקוח קיים, גם אם Address, Phone או פרטי המשלוח שונים. Company Name זהה עם Email שונה = לקוח/איש קשר חדש. |
| אין Email | הבדיקה לפי **Company Name בלבד**. אם השם כבר קיים, הרשומה היא כפילות. |

**התנהגות בעת כפילות:**
- לא נוצרת רשומה חדשה, והרשומה הקיימת לא משתנה.
- גם פרטי המשלוח לא משתנים. נשמרים רק פרטי ה-HBL הראשון.
- Date Added לא מתעדכן.
- לא נשלח מייל.
- אין הודעה או תיעוד למשתמש.

### 4.7 מייל שיווקי ללקוח
- המייל נשלח מתיבת מייל חדשה שמוקדשת למערכת.
- המייל כתוב בעברית, לפי תבנית קבועה עם שדות משתנים מתוך ה-HBL, כולל פרטי המשלוח.
- הנוסח המדויק של התבנית: **TBD**.
- המייל נשלח מיד בסיום העיבוד, ללא אישור ידני.
- אחרי שליחה מוצלחת: Email Status = `Sent`. תאריך השליחה לא נשמר.

#### תנאים לשליחה אוטומטית
כל השדות הבאים חייבים להתקיים:
- Company Name
- Email
- Origin Port
- Origin Country
- Destination Port
- Incoterms
- Shipment Type (FCL/LCL)

Address ו-Phone אינם תנאי לשליחה.

### 4.8 מידע חסר לצורך המייל השיווקי
אם Company Name ו-Email קיימים, אבל חסר לפחות אחד מחמשת פרטי המשלוח:
- המייל השיווקי לא נשלח ללקוח.
- Email Status = `Requires Manual Review`.
- נשלח למשתמש מייל באנגלית, שכולל:
  - את ה-PDF המקורי.
  - את רשימת השדות החסרים.
  - את נוסח המייל השיווקי שהמערכת תכננה לשלוח.

### 4.9 כשל בשליחת המייל
אם שליחת המייל השיווקי נכשלת:
- הלקוח נשמר במאגר.
- Email Status = `Failed`.
- אין ניסיון שליחה חוזר אוטומטי.
- נשלחת למשתמש התראה באנגלית, עם ה-PDF המקורי, סיבת הכשל וכל המידע שחולץ.

### 4.10 התראות למשתמש
מיילי ההתראה נשלחים באנגלית לכתובת קבועה של המשתמש. לפי המקרה, הם כוללים:
- את קובץ ה-PDF המקורי.
- הסבר על מה נכשל או מה חסר.
- את Company Name, אם חולץ.
- את שאר המידע שחולץ, כולל פרטי המשלוח.
- כשחסרים פרטי משלוח: את נוסח המייל השיווקי שתוכנן.

### 4.11 סטטוסים

#### Processing Status
| סטטוס | משמעות |
|---|---|
| `Success` | העיבוד הושלם. אפשרי גם כש-Address או Phone חסרים. |
| `Failed` | Company Name חסר, או שהחילוץ נכשל. |

אחרי תיקון ידני, Processing Status יכול לעבור ל-`Success`. השינוי לא גורם לשליחת מייל.

#### Email Status
| סטטוס | משמעות |
|---|---|
| `Sent` | המייל השיווקי נשלח בפועל. |
| `Missing Email` | לא נמצא Email במסמך. |
| `Email Added Manually` | המשתמש הוסיף Email ידנית. |
| `Requires Manual Review` | חסרים פרטי משלוח שנדרשים למייל. |
| `Failed` | שליחת המייל נכשלה. |

Email Status חייב לשקף את מה שקרה בפועל. אסור להציג `Sent` אם המייל לא נשלח.

### 4.12 שמירת PDF
- קובץ ה-PDF לא נשמר במערכת אחרי העיבוד.
- כשנדרש טיפול ידני או שיש תקלה, ה-PDF המקורי נשלח למשתמש במייל.

### ב. Edge Cases & Error Handling — מקרי קצה וטיפול בשגיאות

| מקרה | התנהגות |
|---|---|
| קובץ שאינו PDF | חסימה והודעה: `Only PDF files are supported.` |
| כשל טכני בהעלאה | הודעת שגיאה באנגלית וכפתור **Try Again**. |
| Company Name חסר | שמירת המידע שחולץ, Processing Status = `Failed`, ללא מייל שיווקי, והתראה למשתמש. |
| Email חסר | שמירה, Email Status = `Missing Email`, ללא מייל שיווקי, והתראה למשתמש. |
| Address או Phone חסרים | שמירה כ-`Success`, תצוגה כ-`NOT Available`, והמייל נשלח אם שאר התנאים מתקיימים. |
| פרט משלוח חסר | שמירה, Email Status = `Requires Manual Review`, ללא מייל שיווקי, והתראה עם רשימת החסרים ונוסח המייל המתוכנן. |
| כשל בשליחת מייל שיווקי | שמירה, Email Status = `Failed`, ללא Retry, והתראה למשתמש. |
| לקוח כפול | דילוג שקט, ללא שינוי ברשומה הקיימת וללא מייל. |
| HBL נוסף לאותו לקוח עם משלוח אחר | מטופל ככפילות. פרטי המשלוח הראשון נשמרים. |
| עריכה ידנית שמשלימה מידע חסר | עדכון הסטטוס הרלוונטי (`Success` או `Email Added Manually`), ללא שליחת מייל. |

## 5. דרישות טכניות ואילוצים

### א. דרישות טכניות
- מערכת Web, בדפדפן במחשב Desktop בלבד.
- ממשק באנגלית. המייל השיווקי בעברית, ומיילי ההתראה באנגלית.
- קלט: PDF דיגיטלי של HBL עם טקסט שאפשר לחלץ.
- אין מגבלה מוגדרת על גודל הקובץ או על מספר העמודים, ואין יעד מוגדר לזמן העיבוד.
- אין Stack טכנולוגי מחייב. **MongoDB מומלץ** כבסיס הנתונים.
- תיבת מייל חדשה וייעודית תחובר למערכת לשליחה בלבד.

### ב. אילוצים
- המערכת מיועדת לשימוש פנימי בחברה בלבד.
- ב-MVP יש משתמש יחיד, ללא Login וללא Roles/Permissions.
- פרטי הלקוחות צריכים להישמר בצורה מאובטחת. לא הוגדרו טכנולוגיית אבטחה, הצפנה או תקן ספציפיים.
- אין דרישה לגיבוי ייעודי.
- אין בדיקה נפרדת שמוודאת שה-PDF הוא אכן HBL לפני החילוץ.
- מסמכי ה-HBL צפויים להיות במבנה דומה, אבל לא בהכרח זהה.
- המערכת לא מנחשת ולא משלימה מידע שלא מופיע במסמך.

#### הנחות
- כל PDF מכיל Consignee אחד בלבד.
- הקבצים דיגיטליים, ואפשר לחלץ מהם טקסט.
