# מסמך דרישות מוצר (PRD) — Ordan Cargo Future Clients

## 1. רקע ומטרות

### א. מטרת המוצר
**Ordan Cargo Future Clients** היא מערכת Web לשימוש פנימי בחברה בלבד. המערכת מחלצת אוטומטית לקוחות פוטנציאליים (לידים) מקובצי PDF מסוג House Bill of Lading (HBL), ושומרת את פרטי ה-Consignee ואת פרטי המשלוח במאגר מסודר.

### ב. תיאור הבעיה
קובצי HBL שמגיעים לחברה מכילים פרטי Consignee שעשויים להפוך ללקוחות של Ordan Cargo. כיום עובדים מחלצים את הפרטים מהמסמכים ובודקים כפילויות באופן ידני, וזה דורש זמן ועבודה.

בנוסף, לעיתים חסרים במסמך פרטים חשובים, או שהחילוץ נכשל. במקרים אלה נדרש מנגנון ברור שמעביר את המקרה לטיפול ידני.

### ג. תיאור הפתרון
המשתמש מעלה ידנית PDF דיגיטלי של HBL, והמערכת מבצעת את שאר התהליך אוטומטית:

1. חילוץ פרטי ה-Consignee: Company Name, Address, Phone ו-Email.
2. חילוץ פרטי המשלוח: נמל מוצא, מדינת מוצא, נמל יעד, תנאי מכר (Incoterms) וסוג משלוח (FCL/LCL).
3. בדיקת כפילות מול מאגר הלקוחות.
4. שמירת לקוח חדש במאגר, כולל פרטי המשלוח.
5. כשחסר מידע חובה או שהחילוץ נכשל: שליחת התראה במייל למשתמש לטיפול ידני, לפי הכללים במסמך זה.

> **מייל שיווקי ללקוח אינו חלק מגרסה זו.** הוא יתווסף רק אחרי בדיקה משפטית ואישור (ראה סעיף 5.ב, TBD).

### ד. חזון ה-MVP ומדדי הצלחה
מטרת ה-MVP היא תהליך אוטומטי מקצה לקצה עבור PDF בודד: העלאה, חילוץ, בדיקת כפילות ושמירה. כשכל הנתונים קיימים, אין צורך בהתערבות ידנית. התערבות ידנית נדרשת רק כשחסר מידע חובה או כשהחילוץ נכשל.

**קריטריוני הצלחה.** במקרים תקינים, המערכת מבצעת ללא התערבות ידנית את כל השלבים הבאים:
1. קבלת ה-PDF ועיבודו.
2. חילוץ נכון של פרטי ה-Consignee ופרטי המשלוח.
3. זיהוי כפילויות לפי הכללים.
4. שמירת לקוח חדש.
5. העברת מקרים חריגים לטיפול ידני באמצעות התראה במייל.

**KPI:** לפחות 90% עיבוד מוצלח.
- **נוסחה:** `מספר הקבצים שהסתיימו ב-Success ÷ (סך ההעלאות פחות הקבצים שזוהו ככפילות)`.
- קובץ שהסתיים ב-`Failed`, או שלא נוצרה ממנו רשומה בגלל כשל חילוץ, נספר ככישלון.

## 2. קהלי יעד וצרכי משתמשים

### א. User Personas — פרסונות משתמשים

#### משתמש המערכת
המשתמש העיקרי הוא עובד החברה שמקבל קובצי HBL ומעלה אותם למערכת. כל מי שנרשם עם חשבון Google (למשל גם מרצה הקורס) יכול להיכנס ולהשתמש במערכת, עם אותן יכולות בדיוק.

המשתמש צריך:
- להעלות קובצי HBL במהירות.
- לסמוך על המערכת שתבצע את עיקר התהליך באופן אוטומטי.
- לצפות ברשימת הלקוחות שנאספו, ולחפש, לסנן ולמיין אותה.
- לזהות במהירות מקרים שדורשים טיפול ידני, ולקבל עליהם התראה במייל.
- לצפות בפרטי לקוח, בפרטי המשלוח ובשגיאות.
- לערוך או למחוק לקוחות לפי הצורך.

### ב. User Stories — סיפורי משתמש

- כמשתמש, אני רוצה להעלות קובץ PDF של HBL, כדי שהמערכת תחלץ ממנו את פרטי הלקוח ופרטי המשלוח באופן אוטומטי.
- כמשתמש, אני רוצה לראות מיד אחרי ההעלאה אם הלקוח נוסף, אם הוא כבר קיים או אם נדרש טיפול ידני, כדי לדעת מה קרה בלי לחפש.
- כמשתמש, אני רוצה שהמערכת תבדוק אם הלקוח כבר קיים, כדי שלא ייווצרו כפילויות.
- כמשתמש, אני רוצה שלקוח חדש יישמר אוטומטית יחד עם פרטי המשלוח, כדי שאוכל לנהל מאגר מסודר של לקוחות פוטנציאליים.
- כמשתמש, אני רוצה לקבל מייל באנגלית עם ה-PDF והסבר כשנדרש טיפול ידני, כדי שאוכל להשלים את התהליך בעצמי.
- כמשתמש, אני רוצה לראות את סטטוס העיבוד של כל לקוח ולסנן לפיו, כדי לאתר במהירות לקוחות שדורשים השלמה.
- כמשתמש, אני רוצה לחפש לקוחות לפי שם, מייל או טלפון, כדי לאתר לקוח במהירות.
- כמשתמש, אני רוצה לפתוח מסך פרטים של לקוח, כדי לראות את כל המידע, כולל פרטי המשלוח והשגיאות.
- כמשתמש, אני רוצה לערוך את פרטי הלקוח ואת פרטי המשלוח, כדי לתקן או להשלים מידע ולסגור מקרים שדורשים טיפול.
- כמשתמש, אני רוצה למחוק לקוח לאחר אישור, כדי להסיר רשומות שאינני רוצה לשמור.

## 3. זרימות וחוויית משתמש

### א. User Journey — מסע המשתמש

#### תרחיש מרכזי: עיבוד מוצלח
1. המשתמש מקבל קובץ HBL, נכנס למערכת עם חשבון Google ומגיע למסך **Clients**.
2. המשתמש עובר דרך סרגל הניווט שבצד למסך **Upload PDF**.
3. המשתמש גורר את ה-PDF לאזור ה-Drag & Drop, או בוחר אותו מהמחשב.
4. העיבוד מתחיל אוטומטית, ומוצג חיווי Processing ברור.
5. המערכת מחלצת את פרטי ה-Consignee ואת פרטי המשלוח.
6. המערכת בודקת אם הלקוח כבר קיים.
7. אם הלקוח חדש וכל שדות החובה קיימים, המערכת שומרת אותו עם Processing Status = `Success`.
8. המשתמש נשאר במסך ההעלאה, ומוצגת ההודעה `Client added successfully.` אזור ההעלאה נשאר זמין להעלאת קובץ נוסף.

#### תרחיש כפילות
1. המערכת מחלצת את פרטי הלקוח.
2. המערכת מזהה, לפי כללי הכפילות, שהלקוח כבר קיים.
3. לא נוצרת רשומה חדשה, והרשומה הקיימת לא משתנה. Date Added ופרטי המשלוח של ה-HBL הראשון נשמרים כמו שהם.
4. מוצגת ההודעה `Client already exists. No changes were made.`

#### תרחיש טיפול ידני
1. המערכת מעבדת את ה-PDF.
2. חסר שדה חובה אחד או יותר, או שהחילוץ נכשל לגמרי.
3. אם חולץ מידע: הרשומה נשמרת עם Processing Status = `Failed` ו-Error Details. אם החילוץ נכשל לגמרי: לא נוצרת רשומה.
4. נשלח למשתמש מייל אחד באנגלית, עם ה-PDF המקורי, הסבר על כל הבעיות וכל המידע שחולץ.
5. מוצגת ההודעה `File processed. Manual review required — details were sent by email.`
6. אם נוצרה רשומה, המשתמש פותח אותה ב-Client Details, משלים את המידע החסר ושומר. אם כל שדות החובה מלאים, הסטטוס הופך ל-`Success`.

### ב. User Flows — זרימות משתמש

#### Flow 0: כניסה למערכת
`פתיחת כתובת המערכת → מסך Sign In → Sign in with Google → בחירת חשבון Google → (בכניסה הראשונה: הרשמה אוטומטית) → Clients`

#### Flow 1: העלאת PDF
`Clients → Upload PDF → Drag & Drop / Choose PDF File → Processing → הודעת תוצאה → Upload PDF נשאר פתוח`

#### Flow 2: צפייה בלקוחות
`Clients → Search / Filter / Sort / Previous–Next → View → Client Details`

#### Flow 3: עריכת לקוח
`Client Details → Edit → שינוי פרטים → Save / Cancel`

בלחיצה על **Save** הנתונים נשמרים כפי שהוזנו, ו-Processing Status מחושב מחדש (סעיף 4.6). אם העריכה יוצרת כפילות, השמירה נחסמת ומוצגת הודעה.

#### Flow 4: מחיקת לקוח
`Client Details → Delete → חלון אישור → Delete → מחיקה סופית → Clients`

אין אפשרות Undo או שחזור.

### ג. UX Requirements — דרישות חוויית משתמש

- ממשק פשוט, נקי ומקצועי.
- כל טקסטי הממשק באנגלית.
- המערכת מיועדת ל-Desktop Web בלבד.
- **סרגל ניווט קבוע בצד שמאל**, ובראשו שם המערכת **Ordan Cargo Future Clients**. פריטי הניווט: **Clients** ו-**Upload PDF**.
- **Clients** הוא מסך הבית וברירת המחדל.
- בזמן עיבוד PDF מוצג חיווי Processing ברור.
- אחרי עיבוד מוצגת הודעה שמתאימה לתוצאה (סעיף 4.3), ללא שם הקובץ.
- ערכים חסרים מוצגים כ-`NOT Available`.
- תאריכים מוצגים לפי אזור הזמן Asia/Jerusalem: בטבלה `Jul 20, 2026`, ובמסך הפרטים `Jul 20, 2026 14:32`.

## 4. דרישות פונקציונליות

### א. Features & Functional Requirements — פיצ'רים ודרישות פונקציונליות

### 4.1 גישה למערכת
- הכניסה למערכת היא **רק באמצעות חשבון Google** (Sign in with Google). אין כניסה עם שם משתמש וסיסמה.
- המערכת **לא שומרת סיסמאות**. Google מאמת את זהות המשתמש.
- **הרשמה אוטומטית:** בכניסה הראשונה עם Google, המשתמש נשמר בטבלת המשתמשים של המערכת. כל חשבון Google יכול להירשם.
- רק משתמשים רשומים נכנסים למערכת. מי שלא נכנס עם Google מועבר למסך **Sign In**.
- טבלת המשתמשים מכילה רק אנשים שנרשמו דרך Google.
- לכל המשתמשים אותן יכולות. אין Roles או Permissions, ואין מסך לניהול משתמשים.

### 4.2 מסך Clients
מסך הבית של המערכת.

#### טבלת לקוחות
עמודות הטבלה:
- **Company Name**
- **Email**
- **Phone**
- **Date Added**
- **Processing Status**
- **Actions**: כפתור **View**.

#### יכולות הטבלה
- **חיפוש** בשדה אחד, לפי Company Name, Email או Phone. חיפוש טלפון מתעלם מכל תו שאינו ספרה. טקסט השדה: `Search by company name, email or phone`.
- **סינון** לפי Processing Status: `All Processing Status`, `Success`, `Failed`.
- **מיון** לפי Date Added. ברירת המחדל: החדשים ראשונים.
- **Pagination** של 25 לקוחות בעמוד, עם כפתורי **Previous** ו-**Next** בלבד, בלי מספרי עמודים ובלי ספירה כוללת.
- כפתור **Refresh** לרענון ידני של הנתונים.
- לחיצה על **View** או על השורה פותחת את מסך **Client Details**.

### 4.3 מסך Upload PDF
- מסך ייעודי להעלאת PDF, עם תמיכה ב-Drag & Drop ובבחירת קובץ מהמחשב.
- קובץ PDF אחד בכל עיבוד, בגודל של עד **4 MB**.
- העיבוד מתחיל אוטומטית מיד אחרי בחירת הקובץ, בלי שלב אישור.
- במהלך העיבוד מוצג חיווי Processing.
- בסיום העיבוד המשתמש נשאר במסך, ואזור ההעלאה נשאר זמין.

#### הודעות במסך

| מצב | הודעה |
|---|---|
| לקוח חדש נשמר עם `Success` | `Client added successfully.` |
| כפילות | `Client already exists. No changes were made.` |
| נשמר עם `Failed`, או שהחילוץ נכשל, וההתראה נשלחה | `File processed. Manual review required — details were sent by email.` |
| נדרש טיפול ידני, אבל שליחת ההתראה נכשלה | `Manual review required, but the notification email could not be sent. Please review the file manually.` |
| הקובץ אינו PDF | `Only PDF files are supported.` |
| הקובץ גדול מ-4 MB | `File is too large. Maximum size is 4 MB.` |
| כשל טכני בהעלאה או בתקשורת | `Something went wrong. Please try again.` וכפתור **Try Again** |

### 4.4 חילוץ מידע מה-PDF
- ה-MVP מיועד לקובצי PDF דיגיטליים של HBL, עם טקסט שאפשר לחלץ. אין צורך ב-OCR.
- בכל מסמך יש Consignee אחד בלבד.
- המערכת לא מנחשת ולא משלימה מידע. כל שדה נלקח רק אם הוא מופיע בפועל במסמך.
- כשה-Consignee הוא "TO ORDER", "TO THE ORDER OF ..." או בנק, ה-Company Name נחשב **חסר**.
- כשמופיעים במסמך כמה מיילים או כמה טלפונים של ה-Consignee, נשמר **הראשון** שמופיע במסמך.

#### שדות לחילוץ ולשמירה ברשומת הלקוח

| קבוצה | שדה | חובה ל-`Success` |
|---|---|---|
| Consignee | Company Name | כן |
| Consignee | Email | כן |
| Consignee | Address | לא |
| Consignee | Phone | לא |
| פרטי משלוח | Origin Port (נמל מוצא) | כן |
| פרטי משלוח | Origin Country (מדינת המוצא שממנה המשלוח יצא בפועל) | כן |
| פרטי משלוח | Destination Port (נמל יעד) | כן |
| פרטי משלוח | Incoterms (תנאי מכר) | כן |
| פרטי משלוח | Shipment Type (`FCL` או `LCL`) | כן |

בנוסף נשמרים:
- **Date Added**: התאריך והשעה שבהם הלקוח נוסף לראשונה.
- **Processing Status**.
- **Error Details**, כשהסטטוס הוא `Failed`.

### 4.5 Processing Status

| סטטוס | מתי |
|---|---|
| `Success` | כל שדות החובה בסעיף 4.4 קיימים. Address ו-Phone יכולים לחסור. |
| `Failed` | חסר לפחות שדה חובה אחד. Error Details מפרט את כל השדות החסרים. |

#### כשל חילוץ מלא
אם אי אפשר לקרוא טקסט מה-PDF, אם קריאת ה-AI נכשלת, או אם היא לא מסתיימת תוך 60 שניות:
- **לא נוצרת רשומה.**
- נשלחת למשתמש התראה עם ה-PDF וסיבת הכשל.

### 4.6 מסך Client Details
מסך נפרד שמציג את פרטי הלקוח בצורה גדולה וברורה.

סדר השדות:
1. **Company Name**
2. **Address**
3. **Phone**
4. **Email**
5. **Origin Port**
6. **Origin Country**
7. **Destination Port**
8. **Incoterms**
9. **Shipment Type**
10. **Date Added**
11. **Processing Status**
12. **Error Details**: מוצג רק כשהסטטוס הוא `Failed`.

#### עריכה
- כפתור **Edit**. במצב עריכה מוצגים הכפתורים **Save** ו-**Cancel**. Cancel מחזיר את הערכים המקוריים.
- ניתן לערוך את כל השדות 1–9.
- הנתונים נשמרים בדיוק כפי שהוזנו, ללא ולידציה של פורמט.
- **אחרי Save**, Processing Status ו-Error Details מחושבים מחדש:
  - כל שדות החובה מלאים: הסטטוס הוא `Success`, ו-Error Details מתרוקן.
  - חסר שדה חובה: הסטטוס הוא `Failed`, ו-Error Details מפרט את השדות החסרים.
- **עריכה שיוצרת כפילות** של לקוח אחר, לפי כללי סעיף 4.7, נחסמת. הנתונים לא נשמרים, ומוצגת ההודעה `A client with this company name and email already exists.`
- לא נשמר Last Updated.

#### מחיקה
- לפני המחיקה מוצג חלון אישור, עם הטקסט `Are you sure you want to delete this client?`
- אחרי האישור, המחיקה סופית ומיידית, ללא Undo או שחזור.

### 4.7 מניעת כפילויות
המערכת בודקת כפילויות לפני שהיא יוצרת לקוח חדש, וגם בעת עריכה.

| מה קיים ברשומה החדשה | כלל |
|---|---|
| Company Name ו-Email | **Company Name זהה + Email זהה** = לקוח קיים, גם אם שאר השדות שונים. Company Name זהה עם Email שונה = לקוח חדש. |
| Company Name בלבד | **Company Name זהה** = לקוח קיים. |
| Email בלבד | **Email זהה** = לקוח קיים. |
| אף אחד מהם | אין בדיקת כפילות. נוצרת רשומה חדשה. |

ההשוואה מתעלמת מהבדלי אותיות גדולות וקטנות ומרווחים מיותרים.

**התנהגות בעת כפילות בהעלאה:**
- לא נוצרת רשומה חדשה, והרשומה הקיימת לא משתנה. גם פרטי המשלוח לא משתנים: נשמרים רק פרטי ה-HBL הראשון.
- Date Added לא מתעדכן.
- לא נשלחת התראה.

### 4.8 התראות למשתמש
- ההתראות נשלחות במייל, באנגלית, מתיבת המייל הייעודית של המערכת לכתובת קבועה של המשתמש.
- התראה נשלחת **רק** כשנדרש טיפול ידני: כשהרשומה נשמרה עם `Failed`, או כשהחילוץ נכשל לגמרי.
- **התראה אחת לכל קובץ**, שמפרטת את כל הבעיות שנמצאו.
- תוכן ההתראה:
  - את קובץ ה-PDF המקורי, כקובץ מצורף.
  - את רשימת השדות החסרים, או את סיבת הכשל.
  - את כל המידע שחולץ.
  - ציון אם נוצרה רשומה במערכת.
- אין ניסיון שליחה חוזר אוטומטי. אם שליחת ההתראה נכשלה, מוצגת הודעה מתאימה במסך ההעלאה (סעיף 4.3).

### 4.9 שמירת PDF
- קובץ ה-PDF לא נשמר במערכת, גם לא באופן זמני מעבר לזמן העיבוד.
- כשנדרש טיפול ידני, ה-PDF המקורי מצורף להתראה.

### ב. Edge Cases & Error Handling — מקרי קצה וטיפול בשגיאות

| מקרה | התנהגות |
|---|---|
| קובץ שאינו PDF | חסימה והודעה: `Only PDF files are supported.` |
| קובץ גדול מ-4 MB | חסימה והודעה: `File is too large. Maximum size is 4 MB.` |
| כשל טכני בהעלאה | הודעת שגיאה וכפתור **Try Again**. |
| PDF בלי טקסט, כשל AI או חריגה מ-60 שניות | לא נוצרת רשומה, ונשלחת התראה עם ה-PDF וסיבת הכשל. |
| שדה חובה אחד או יותר חסר | שמירה עם `Failed`, ו-Error Details מפרט את כל השדות החסרים. נשלחת התראה אחת. |
| Address או Phone חסרים | שמירה עם `Success`, ותצוגה כ-`NOT Available`. |
| Consignee הוא "TO ORDER" או בנק | Company Name נחשב חסר. |
| כמה מיילים או טלפונים | נשמר הראשון במסמך. |
| לקוח כפול | אין רשומה חדשה ואין שינוי ברשומה הקיימת. מוצגת הודעת כפילות. |
| HBL נוסף לאותו לקוח עם משלוח אחר | מטופל ככפילות. נשמרים פרטי המשלוח הראשון. |
| חסרים גם Company Name וגם Email | אין בדיקת כפילות. נוצרת רשומה חדשה עם `Failed`. |
| עריכה שמשלימה את כל שדות החובה | הסטטוס הופך ל-`Success`. |
| עריכה שמוחקת שדה חובה | הסטטוס הופך ל-`Failed`. |
| עריכה שיוצרת כפילות | השמירה נחסמת, ומוצגת הודעה. |
| שליחת התראה נכשלה | אין ניסיון חוזר. מוצגת הודעה מתאימה במסך ההעלאה. |

## 5. דרישות טכניות ואילוצים

### א. דרישות טכניות
- מערכת Web, בדפדפן במחשב Desktop בלבד.
- ממשק באנגלית. גם מיילי ההתראה באנגלית.
- קלט: PDF דיגיטלי של HBL עם טקסט שאפשר לחלץ, בגודל של עד 4 MB.
- זמן מקסימלי לחילוץ ה-AI: 60 שניות.
- אזור זמן לתצוגה: Asia/Jerusalem.
- אין Stack טכנולוגי מחייב. **MongoDB מומלץ** כבסיס הנתונים.
- תיבת מייל ייעודית תחובר למערכת לשליחת התראות בלבד.

### ב. אילוצים
- המערכת מיועדת לשימוש פנימי בחברה בלבד.
- הגישה מוגנת בכניסה עם Google בלבד. כל חשבון Google יכול להירשם, ללא Roles/Permissions.
- פרטי הלקוחות צריכים להישמר בצורה מאובטחת.
- המערכת לא מנחשת ולא משלימה מידע שלא מופיע במסמך.
- מסמכי ה-HBL צפויים להיות במבנה דומה, אבל לא בהכרח זהה.
- אין בדיקה נפרדת שמוודאת שה-PDF הוא אכן HBL לפני החילוץ.

#### הנחות
- כל PDF מכיל Consignee אחד בלבד.
- הקבצים דיגיטליים, ואפשר לחלץ מהם טקסט.
